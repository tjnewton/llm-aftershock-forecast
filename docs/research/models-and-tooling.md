### Per-model notes

**1. Qwen3.8-27B** [S1,S2,S4,S5]
- A dense vision-language model (`Qwen3_5ForConditionalGeneration`, `model_type: qwen3_5`, pipeline `image-text-to-text`). It has 64 layers in a hybrid Gated DeltaNet + Gated Attention layout. config `text_config.max_position_embeddings` = 262144.
- **Cutoff: not documented.** I checked the model card, config.json, generation_config.json and chat_template.jinja. The card cites only a blog post (`qwen.ai/blog?id=qwen3.8`, Aug 2026) as its reference; that page renders by JS and returned no text [S4]. A web search found no Qwen3.8 technical report [S5]. Because the weights were published in Aug 2026, treat **all of 2025 as possibly in training data**.
- Thinking is on by default. Turn it off per request with `chat_template_kwargs: {"enable_thinking": false}`. The template then emits an empty `<think>\n\n</think>\n\n`.
- `reasoning_effort` is read by the chat template and accepts only `xhigh` (default), `medium` or `low`. **Any other value, including `high`, raises a template exception.** `xhigh` and `low` inject a sentence into the system turn; `medium` injects nothing.
- `preserve_thinking` defaults to true, so earlier turns' `<think>` blocks stay in the prompt. Set `chat_template_kwargs: {"preserve_thinking": false}` to drop them.
- Recommended sampling: thinking T=1.0, top_p 0.95, top_k 20. Non-thinking: T=0.7, top_p 0.8, top_k 20, presence_penalty 1.5. generation_config sets `do_sample: true, temperature 1.0`.

**2. gpt-oss-20b** [S6,S7,S8]
- Model card (arXiv 2508.10925, §2.4) says the models have "a knowledge cutoff of June 2024". The chat template also hard-codes `Knowledge cutoff: 2024-06`.
- Harmony format is required: the card says the models should "only be used with the harmony format". The template maps a `system`/`developer` first message into a developer `# Instructions` block. The real system block is generated by the template.
- **Quirk for backtesting:** the template injects `Current date: {{ strftime_now("%Y-%m-%d") }}`, i.e. the wall-clock date. To hide the date in a hindcast you need a custom `--chat-template-file`.
- Reasoning effort is `low`, `medium` (template default) or `high`. Set it with the `reasoning_effort` template kwarg; the template writes it as `Reasoning: <level>` in the system message, and the card says it can be set in the system prompt, e.g. "Reasoning: high".
- `config.json`: 24 layers, YaRN factor 32 over 4096, so 131,072 positions. The model is MXFP4-native and the card says 20b "run within 16GB of memory".

**3. gpt-oss-120b** [S6,S9]: 116.83B total safetensors bytes; 36 layers. MXFP4 GGUF is 63.39 GB. **Excluded:** it does not fit 48 GB unified memory.

**4. Alternatives with a documented cutoff** [S10–S14]
- **Olmo 3.1 32B Instruct (best pick for contamination control).** The card says "**Date cutoff:** Dec. 2024". Training data is fully open (Dolma 3/Dolci). Quirk: when no system message is given, the template injects "You are Olmo… Your date cutoff is December 2024…". Context is 65,536 (YaRN factor 8 over 8192). Q4_K_M is 19.48 GB, which fits both machines.
- **Gemma 4 31B-it / 26B-A4B-it.** The card says the pre-training data has "a cutoff date of January 2025". Thinking is off by default; `chat_template_kwargs: {"enable_thinking": true}` inserts `<|think|>` into the system turn. With thinking off, the 31B and 26B models still emit an empty `<|channel>thought\n<channel|>` block. Recommended sampling is T=1.0, top_p 0.95, top_k 64. The card also says thoughts from previous turns must not be fed back. The 26B-A4B MoE is the fast option, with 3.8B active parameters.
- Also documented, but older: `mistralai/Mistral-Small-24B-Instruct-2501`. Its card's system prompt says "Your knowledge base was last updated on 2023-10-01" [S14]. `google/gemma-3-27b-it` is gated and its card was not readable without login [S15].
- Checked with no cutoff found by grep: Mistral-Small-3.2-24B-2506, OLMo-2-0325-32B, granite-4.1-30b, granite-4.2-30b [S14].

Determinism caveats [S24]:
- With `cache_prompt` (default true), "the logits are **not** guaranteed to be bit-for-bit identical for different batch sizes". For strict reproducibility send `cache_prompt: false` and run `--parallel 1`. For throughput, accept small drift.
- Metal and CUDA outputs will not match bit-for-bit even with the same seed.

Other notes:
- v0.7.0 changed the default port from 8080 to **9931** [S20].
- GGUF repo READMEs show a new `llama serve -hf <repo>` CLI [S3,S9].

**Recommendation: use llama.cpp `llama-server` (v0.7.0 / latest `bNNNNN`) on both machines.**
- One engine, one set of GGUF files and one HTTP contract on both boxes.
- OpenAI-style `response_format` with `json_schema` is enforced by grammar, plus per-request `seed`/`temperature` and `--parallel` slots.
- Mac: Homebrew bottle. Windows: prebuilt CUDA 13.4 zip with sm_120a.
- Ollama is the runner-up. It has native Windows support and a `format` schema, but less control over templates and caching.
- MLX-LM fails the structured-output requirement, and vLLM fails native Windows.
- Smoke-test that grammar + thinking coexist for each model. The chat-session layer builds the combined grammar (`server-common.cpp` drops `json_schema` once the session grammar is set) [S25].

**anthropic SDK** [S44]
- `client.messages.parse(..., output_format=<pydantic model>)` exists in `src/anthropic/resources/messages/messages.py`, with both `output_config` and `output_format` parameters. `examples/structured_outputs.py` uses it and reads `.parsed_output`.
- CHANGELOG 0.77.0 (2026-01-29) says "add support for Structured Outputs in the Messages API" and "migrate sending message format in output_config rather than output_format". 1.9.0 (2026-09-28) says "accept diagnostics in stream() and parse()".
- The **README does not document `parse`/`output_config`**. It points to platform.claude.com docs, and helpers.md/api.md have no mention either.

**pycsep** [S41]
- **The Brier score is in, from 0.7.0.** The CHANGELOG under v0.7.0 says "Implementation of the Brier Score and its consistency test (#232)". 0.8.0 added plot refactoring and PEP 660.
- Licence BSD-3-Clause. The repo moved to `cseptesting/pycsep`.

**floatcsep**: BSD-3-Clause. Last push 2026-10-14. Pinned `<3.13` [S42].

**Mizrahi `etas`** [S43]
- MIT licence. Latest commit `097f08b69a`, 2026-04-10T16:56:12Z (merge PR #21). Latest GitHub release `3.2` is from 2023-01-30, while pyproject says `version = "3.0.0"`.
- **Not on PyPI** (404). Install with `pip install git+https://github.com/lmizrahi/etas`, per the README; pin a commit SHA.
- pyproject has `requires-python = ">=3.12"`. Deps are unpinned (geopandas, numpy, pandas, pynverse, scipy, Shapely, tabulate). `requirements.txt` pins old versions (numpy 2.0.1, pandas 2.2.2) plus a git-only `hermes-model` that only the `hermes` extra needs.

**Python recommendation: 3.12.**
- It is the only minor version every hard requirement allows: floatcsep `<3.13`, etas `>=3.12`, numpy 2.5 / scipy 1.18 / rasterio / pyproj `>=3.12`.
- pycsep's CI tops out at 3.12.
- Every other package lists 3.12 or ships py3 wheels.
- 3.13 would break floatcsep and drop pycsep outside its tested range. If floatcsep is dropped, 3.13 becomes possible, but pycsep is still untested there.
